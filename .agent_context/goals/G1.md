## 2. Data flow

```
Claude Code / Codex / OpenCode / Copilot / Pi
   -> hook (vibebuddy-hook): privacy filter, host + tty detection
   -> POST 127.0.0.1:7331/v1/{claude,codex,agent}-hooks   (0.5 s timeout, silent on failure)
Other producers -> POST /v1/events   (generic task.start / task.progress / task.done)
GitHub Actions  -> daemon ci.rs polls every 30 s (no hooks)

vibebuddyd
   adapters (translate only, no state)  -> activity.rs aggregator (<= 3 task cards, TTL sweep every 60 s)
   -> visible state snapshot (deduplicated) + announcement edges (occasions.rs)
   -> Transport to the box, by priority:
        1. USB serial   serial_transport.rs  (VID:PID 303A:1001, bounded queue of 64)
        2. LAN          lan.rs               (TCP 7340, Noise IK, mDNS _vibebuddy._tcp)
        3. Relay        relay.rs             (WSS, wss://relay.korekore.ai or -staging, /v1/boxes/<id>)
   <- box -> daemon: button events, boot lines (BOX KEY, DISPLAY READY BUILD, RELAY URL, WIFI ADDRESS), heartbeats, voice.* acks
   -> HTTP API: /v1/status, /v1/status/stream (SSE), /v1/config, /v1/device/*, /v1/updates/check
        <- macOS app (DaemonClient.swift, supervises the daemon as a helper)
        <- Linux app (desktop/src/client.rs, systemd supervises the daemon)
```

Key points:

- **Single writer per box.** Only the daemon touches the serial port or the Relay. The CLI and apps go through HTTP (`docs/architecture.md` decision 2).
- **Ordering of transports.** CONTEXT.md ("Link") says USB wins, then LAN, then Relay. The daemon's `Transport` trait (`serial_transport.rs` L91) is the seam; `lan.rs` and `relay.rs` are the other two implementations' pieces.
- **Relay config flows from the computer.** On USB the daemon sends `device.relay.set` (`docs/protocol.md`, "Relay"); the box stores it in the `link` partition. The daemon picks its Relay from `VIBEBUDDY_RELAY_URL`, then the update manifest's `relay` (release builds only), then the build default (`relay.rs` L35-36).
- **Pairing and takeover.** Pairing is a stored key per computer and box (ADR-0012, `link` partition, ADR-0014). Takeover rules are in `docs/protocol.md` "Pairing": free, last linked, or gone for 10 minutes; `takeover:true` always wins unless USB is in use. The loser gets `link.unlinked` with `reason` `takeover`, `usb` or `unpaired`.
- **LAN and Relay are encrypted with Noise.** `docs/protocol.md` "Local network link" describes `Noise_IK_25519_ChaChaPoly_SHA256` with prologue `vibebuddy-link-v2`; code in `firmware-rs/core/src/noise.rs` and `daemon/src/noise_link.rs`. The ADR for this is still `proposed` (see section 6).
- **Agent setup is written by the hook, not the apps.** The Mac app asks the hook for agent-owned files (`vibebuddy-hook agent-file`, `HookInstaller.swift` L137). On Linux, `vibebuddy-hook install|uninstall|status|plan` does it. Both apps must follow the same merge rules; `HookConfig.swift` and `hook/src/install.rs` implement them separately (CONTEXT / decision 15).
- **Activities expire.** Working after 30 min without events, needs-input after 4 h (`activity.rs` L21-23). A sweep runs every 60 s (`main.rs` L55, L1114).
- **K2 source focus.** The daemon routes device button events to `source_opener.rs`, which opens the agent's desktop app, its terminal tab (AppleScript on Mac, Hyprland on Linux) or tmux pane.
- **Firmware and character updates.** The apps show the update manifest; the daemon fetches `https://updates.korekore.ai/vibebuddy/manifest.json` (`updates.rs` L20) and streams the firmware to the box over the same link (`/v1/device/firmware`). Resumable transfer over any link (ADR-0016) is not implemented yet.
- **Bluetooth** does not appear anywhere in the code. It is only mentioned in historical docs.

## 3. Device-specific vs portable

Device-specific (board: ATK-DNESP32S3-BOX V1.1, ESP32-S3 N16R8, per `docs/hardware.md`):

- Pin map and peripheral setup: `firmware-rs/device/src/main.rs` header L4-11 and L341-396. Key facts: UART0 TX/RX 43/44 (CH343 bridge). I2C0 SDA/SCL 48/45 carries the XL9555 expander (0x20), ES8311 codec (0x18), and optionally a touch controller (0x2E). LCD: ST7789, 8-bit i8080, CS/DC/RD/WR 1/2/41/42, data 40/39/38/12/11/10/9/46. I2S 21/13/14. K0 is GPIO0. K1 and K2 come from XL9555 P0.4 and P0.3, active low. Backlight is P0.7, speaker enable P0.5.
- Chip config: `firmware-rs/device/.cargo/config.toml`, `rust-toolchain.toml` (`esp` channel).
- Flash layout: `firmware/partitions.csv` (16 MB, two OTA app slots, `voices` at 0x410000, `link` at 0xa12000). Used by both firmwares.
- Bootloader: `firmware-rs/bootloader`.
- The C twin of all of the above lives in `firmware/main/agent_display.c`, `agent_audio.c`, `agent_buttons.c`, and so on.
- Touch is not universal: `docs/hardware.md` says some boxes answer at 0x2E and some don't. Firmware must probe and fall back to buttons. Per the code, touch is not implemented yet.
- USB VID:PID `303A:1001` is the ESP32-S3's USB Serial/JTAG ID, not the board's. Other firmware (Muse) can enumerate with the same ID, so the daemon must watch for `ESP-ROM:` and ESP-IDF log lines (CONTEXT / architecture decision 17). This is a portability hazard for any second board.

Portable (no board knowledge):

- `firmware-rs/core`: state machine (pomodoro, leisure, menu, boredom), rendering (`canvas`, `text`, `look`), protocol parsing, Noise, OTA logic, storage format, character/voice pack parsing, audio sequence (`audio.rs` as register/timing data). Tested with `cargo test -p vibebuddy-firmware-core`. A new board needs a new `device/` layer that implements `Board`, not changes to core. The LCD and codec register sequences are the exception: they are chip-specific and live in core for testability.
- `protocol/`, `daemon/`, `hook/`, `manifest/`: no board names, except the VID:PID above and the board identifier string `atk-dnesp32s3-box` reported by the firmware (used for display only).
- `desktop/` and `app/`: they talk to the daemon over HTTP and know nothing about the board's hardware.
- Character packs (`characters/`, `character_pack.rs`): they carry a 320x240 look as four key frames, audio and names. Their size limits (`character_pack.rs` L29-35) depend on the partition size.

## 4. Platform split (Mac and Linux)

- Same daemon, same hook, same firmware. The daemon is the only place device logic exists.
- macOS: the app bundles `vibebuddyd` and `vibebuddy-hook` into Application Support, supervises the daemon, sends the link-lost notification (`Notifier.swift`), runs Sparkle and the DMG, and owns onboarding.
- Linux: systemd user units run the daemon, `vibebuddy-hook install` writes agent config, the daemon sends link-lost via `notify-send` (`link_alert.rs` L1), and the tray is StatusNotifierItem.
- AGENTS.md requires feature parity; nothing in the repo checks it mechanically. `docs/architecture.md` decision 15 describes the Linux substitutes (systemd, `notify-send`, `vibebuddy-hook install`). Any Mac-only feature needs a stated Linux equivalent in the same PR.

## 6. Notable inconsistencies between docs and code

1. **`docs/architecture.md` is out of date on transports.** It says "The first version implements only `SerialTransport`" and the data flow shows USB only. The daemon now has LAN (`lan.rs`), Relay (`relay.rs`) and a `Transport` trait. Also, the `beacon` component (L18-22) is not in the code, and no CLI binary exists.
2. **ADR-0015 is `proposed`, but its code is shipped.** `noise.rs` (core), `noise_link.rs` (daemon), and `docs/protocol.md` describe Noise as current behaviour. Either the ADR status or the rollout claim is wrong.
3. **ADR-0016 is `proposed`** and matches the code (no resumable transfer exists). Consistent, but the apps and docs should not promise it.
4. **Two ADRs numbered 0007**: `0007-device-menu-behind-a-long-k1.md` and `0007-lines-are-written-in-advance.md`. The ADR index is ambiguous.
5. **Voice pack vs Character pack.** CONTEXT.md says "voice pack" is the old term and "Character pack" is the name. Code still uses the old term widely: `firmware-rs/core/src/voice_pack.rs`, `daemon/src/voice_writer.rs`, `app/Sources/VibeBuddyCore/VoicePack.swift`, `firmware/main/agent_voice_pack.c`, `tools/make_voice_pack.py`, the `voice.*` protocol events, and the `voices/` directory. `docs/protocol.md` and `docs/firmware-bringup.md` also say "voice pack". The rename is only partial; `character_pack.rs` and `characters/` are the new names.
6. **`firmware/` is not only a fallback.** The Rust build reads `firmware/partitions.csv` (`tools/build-firmware.sh`), so a change to the C tree can break the Rust firmware.
7. **Stale file reference.** `hook/src/filter.rs` L3 cites `tools/hook_filter.py`, which no longer exists (the hook is Rust since ADR-0005).
8. **Hardware doc has a contradictory top section.** `docs/hardware.md` says "no GPIOs are frozen until the PCB silkscreen is confirmed" and lists the pinout as "provided by the user, not yet verified". Later sections record on-hardware verification of the same pins, and the firmware uses them. The top section should be updated.
9. **Repo name vs hardware.** The directory is `vibebuddy-cardputer` and `.vscode/settings.json`, `G2.md`, and `G3.md` mention "cardputer", but the target is an ATK-DNESP32S3-BOX (`docs/hardware.md`). No doc says Cardputer. Treat the name as a leftover.
10. **Pre-release naming in docs.** `docs/stage-*.md` and `protocol.md` "Stage 1 error output" describe a staged plan. `docs/stage-2.md` L18 says `beacon` was not built; `docs/roadmap.md` L49 still lists it as Stage 6 work. Stage docs read as history, not current design.
11. **`docs/architecture.md` decision 4 vs `docs/hardware.md`.** Architecture says GPIOs must come from official docs or on-device verification. The firmware pins match the on-device-verified set in `docs/hardware.md`, so this is consistent, but the firmware source doesn't cite that doc.
12. **`just test` vs CI.** `just test` omits clippy, localization and Python tests, which CI runs. A release can pass `just test` and still fail CI.
13. **Touch and buzzer.** `docs/hardware.md` lists touch, buzzer, microphone as pending; the firmware has none of them wired. Consistent, but worth knowing before planning UI changes that assume touch.

## 7. Where to start for common changes

- New UI string in the apps: `app/Localization/`, `desktop/src/i18n.rs`, `tools/check-localization.py`.
- New event between agent and device: `daemon/src/activity.rs` and `firmware-rs/core/src/link.rs` (or `lan.rs` / `relay_box.rs`), plus `docs/protocol.md`.
- New agent: `hook/src/` (adapter + `install.rs`), `app/Sources/VibeBuddyCore/HookConfig.swift`, `desktop/src/agents.rs`.
- New screen or animation: `firmware-rs/core/src/{leisure,menu,look,canvas}.rs`, previewed with `tools/preview-*.sh`.
- New board: new `firmware-rs/device` layer implementing `Board`; keep `core` free of pins.
