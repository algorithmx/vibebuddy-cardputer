# Goal
Based on the investigation of Goal #2 `G2.md` and the architecture knowledge recorded in `G1.md`, find out the minimal core of the present project (after adaptation to M5Stack Cardputer-Adv device), propose a minimized version of the present project to keep only the essential capabilities.

# Results

Status: proposal, 2026-10-16. Nothing has been removed from the code. The proposal needs a decision on the open questions at the end before any code is cut.

## 1. What the Cardputer-Adv can carry

From G2 (plan and the on-device probes):
- 8 MB flash, no PSRAM. The 8 MB flash holds two app slots and the voices. The app is 2.8 MB, so an app slot is 3 MB.
- Internal RAM is the limit. The static RAM and heap regions come to about 172 KB, plus the heap regions (about 164 KB). The Wi-Fi driver needs internal RAM too. Together this is probably over the usable budget (see G2, memory). The first device run will show the real figure from the `MEMORY INTERNAL` line.
- Display 240x135, one 5x7 font, three keys (K0 = G0, K1 = `;`, K2 = `.`), an ES8311 speaker and codec, microSD, IR, battery ADC, Grove, and an IMU (not used).

So the constraint that shapes the minimal core is memory, not flash: a link that needs Wi-Fi (the LAN and Relay paths, with TLS and Noise) is the first thing to question.

## 3. Proposal: three profiles

### Profile A, "core" (recommended first Adv firmware)
Keep:
- USB serial link to the computer (the cable path). The protocol and `Firmware::receive` as they are.
- Duty display: the pet, task cards (up to three), the idle line, the state labels, the badge.
- Pomodoro (K0 start, pause, skip) with the daily tally.
- Buttons K0, K1, K2 as the core uses them, mapped by `core::board::KEY_MAP` (K1 `;`, K2 `.`).
- Menu, reduced to: stop focus, volume, mute, status. Computers, network and the Wi-Fi setup are removed from the menu.
- Speaker playback of the built-in voice, if memory allows (see the open questions).

Drop from the Adv build (feature-gated, not deleted from the repo):
- Wi-Fi, the LAN link, mDNS, the Relay, Noise sessions and pairing (`net.rs`, `relay.rs`, `lan.rs`, `relay_box.rs`, `noise.rs`, `link.rs` for the network path). This frees the largest share of internal RAM and the Wi-Fi driver's buffers.
- OTA over the network (`ota.rs`). Updates come over USB with `tools/flash.sh`.
- The network settings, computers, and network status in the menu.

Keep as is, unchanged: the state machine, the protocol, the duty display, the pomodoro, the leisure skits, the look, the storage format for Characters.

Estimated saving: the Wi-Fi/Relay/Noise/LAN code plus its buffers. The G2 static RAM figure (about 172 KB, of which the heap regions are about 164 KB) is the main budget item; this profile makes it the first thing to shrink.

### Profile B, "core + voice" (the first profile with spoken lines)
Profile A plus the voices partition and the playback path, which the user asked to keep. The voices partition is 1.75 MB on the Adv (the voice pack is about 1.2 MB). This profile must confirm the speaker on the board before anything else is added.

### Profile C, "full"
The full firmware: Wi-Fi, LAN, Relay, Noise, OTA. Not feasible on the Adv without PSRAM unless the internal-RAM measurement (see G2) shows room. Kept as the box's profile.

## 4. What this means for the apps and the daemon (AGENTS.md parity)

The Mac and Linux apps show the device's network features (computers, network status, the LAN and Relay paths). With Profile A, the Adv offers only the USB link, so the apps need to:
- report that the device has no network link (the status says USB only), and
- hide or disable the network options when the connected device is an Adv.

This is a user-visible change on both platforms, so it must land in the same change in `app/` and `desktop/`, with zh-Hans strings. It is Phase C work, not part of this proposal's code.

## 5. Risks

- Profile A changes the product: the Adv is a USB-only buddy. The Relay and LAN features will not reach it.
- The memory figure is estimated. The first device run decides whether Profile B fits.
- The menu change affects the `menu_preview` docs (`docs/device-menu.md`), which must be updated with the Adv's menu.

## 6. Decisions needed

1. Profile A first, or Profile B from the start? (Recommendation: A first, then B once the speaker is confirmed and the memory figure is known.)
2. Should the Adv drop the network features entirely, or keep them behind a build flag for a later try? (Recommendation: a build flag, so nothing is deleted.)
3. Is the Adv's menu allowed to differ from the box's? AGENTS.md parity says the matching change lands on both apps; the device menu is the device's own. (Recommendation: yes, with the difference written in the docs.)
